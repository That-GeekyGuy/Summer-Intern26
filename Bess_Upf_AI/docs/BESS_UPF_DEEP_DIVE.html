1 Project Purpose & Domain Context

BESS-UPF AI is an intelligent monitoring and analysis platform for 5G User Plane Functions (UPF). Before diving into code, understanding the telecom context is critical.

What is a UPF?

In 5G, the User Plane Function is the network element that actually moves data packets for mobile subscribers. It sits between the Radio Access Network (RAN) and the internet. Every YouTube video, WhatsApp message, and web request from a 5G phone goes through a UPF.

What does this project do?

It collects UPF performance metrics, runs three tiers of anomaly detection, generates capacity forecasts with OLS regression, and exposes a conversational LLM interface so operators can ask questions like "Why are sessions spiking?" in plain English.

All throughput values are in bytes/s, not bits/s. The frontend formatter (fmtBytes) displays "GB/s", not "Gbps". 10 GB/s = 80 Gbps. Never confuse these in cross-questioning — the detection capacity ceiling is 10_000_000_000 (10 GB/s = 10 billion bytes/s).

Why is metrics-backend "internal: true"?

Security isolation. The VictoriaMetrics database, MinIO store, and all ML models run on a network with no outbound internet access. If any service is compromised, it cannot phone home, exfiltrate data, or download additional payloads. The only internet-capable service is vLLM (to download model weights from HuggingFace) and Caddy (for ACME Let's Encrypt in production).

Critical: Bind Mount vs Named Volume

The ./models directory uses a bind mount (not a named Docker volume). This means the path exists on the host filesystem and you can copy trained model files there directly. Named volumes like vllm-cache live inside Docker's storage and require docker volume commands to inspect. The bind mount allows retraining scripts to write directly to ./models/ without needing to exec into a container.

The simulator uses a sine wave to model real-world traffic patterns:

// Variation: ±30% from base (700k–1.3M sessions at 1M base)
jitter  := 1.0 + (rand.Float64()*0.04 - 0.02)  // ±2% random noise

How Counter Semantics Work

Prometheus Counters can only increase. The simulator models per-second rates and calls counter.Add(rate × dt) each tick. In flatline mode, rate → 0, so the counter stops incrementing (stays flat) — it doesn't reset to zero. In Prometheus, you then use rate(counter[5m]) → 0 to detect the flatline. This is why dropping to zero traffic with a flatline is detectable even though the raw counter doesn't decrease.

N3 vs N6 Traffic Asymmetry

// N3 (RAN-facing) carries slightly more traffic than N6 (internet-facing)
"rx/N3": sessions * bps * 1.2,   // 120% — users downloading from internet → high inbound
"tx/N6": sessions * bps * 1.2,   // 120% — UPF sending to internet
"tx/N3": sessions * bps * 0.8,   // 80%  — UPF sending to phones (uploads are smaller)
"rx/N6": sessions * bps * 0.8,   // 80%  — from internet (acknowledgments, etc.)

Z-Score Rule (zscore.go)

This is the most important Tier 1 rule — it flags the latest data point when it's statistically extreme vs. the window baseline.

// ZScore computation — note the crucial design choice:
baseline := values[:len(values)-1]  // ALL values EXCEPT the latest
latest   := values[len(values)-1]

mean = sum(baseline) / len(baseline)
std  = sqrt(sum((v - mean)² for v in baseline) / len(baseline))

if std < 1e-10 { return nil }  // flat line — skip (avoids division by zero)

z = (latest - mean) / std
if |z| >= threshold { fire anomaly event }

Why exclude the latest value from the baseline?

If the spike value were included in the mean/std calculation, it would inflate both statistics, potentially reducing its own z-score and self-suppressing the alert. By computing mean/std from the window minus the last point, a genuine spike cannot hide itself in the distribution.

MetricZ-score thresholdSeverityRationale
pfcp_sessions_total2.5high4× spike ≈ z > 100 vs baseline; fires on first spike sample
port_bytes_count2.5highTraffic bursts are serious but not immediately critical
port_dropped_count2.0criticalDrops are always serious — lower threshold, higher severity

Trend Rule

Fits an OLS line to all values except the last, then checks if the latest point deviates from the predicted value by more than deviation_threshold (20-25%).

// Simplified:
predicted := olsLine.predict(latestTimestamp)
deviation := |latest - predicted| / predicted
if deviation > deviation_threshold { fire "trend" event }

Threshold Rule

Simple bounds check on the latest value:

if threshold.Max != nil && latest > *threshold.Max { fire critical }
if threshold.Min != nil && latest < *threshold.Min { fire warning }

Configured in rules.yml: pfcp_sessions_total threshold max = 2,000,000 (20 lakh per node). A session spike to 40 lakh will hit this.

7 Tier 3 OLS Predictive Forecasting

This runs after Tier 1 each poll and predicts capacity breaches before they happen. Located in detection/internal/detector/forecaster.go.

OLS Linear Fit (olsLinearFit)

// Ordinary Least Squares: fits y = a + b*x where x is 0-based sample index
// (using index instead of raw timestamps avoids float64 cancellation at large Unix timestamps)

n := float64(len(values))
// sums for OLS formula
sumX, sumY, sumXY, sumX2 := ...

denom := n*sumX2 - sumX*sumX
b = (n*sumXY - sumX*sumY) / denom   // slope
a = (sumY - b*sumX) / n             // intercept

// R² (goodness of fit):
r2 = 1 - ssResiduals/ssTotal

Fire Logic

// Steps ahead to horizon (1h ahead by default):
stepDur := window / (n-1)           // time between samples
stepsAhead := horizon / stepDur     // how many steps is 1h away?
predictedAtHorizon := a + b*(n-1 + stepsAhead)

// Fire if:
// Capacity target: predicted value crosses capacity ceiling within horizon
shouldFire = predictedAtHorizon >= capacity

// Drop-rate target (accel_only: true): fire if slope is positive
shouldFire = b > 1e-10 && currentValue > 0

Deduplication

To avoid flooding operators with repeated alerts during a sustained trend, the forecaster checks if a predictive event for the same metric+labels was emitted within horizon/2 = 30 minutes. If yes, the event is suppressed. This means at most one predictive event per metric per 30 minutes.

Why use rate() for counter metrics in the forecaster?

port_bytes_count and port_dropped_count are Prometheus Counters (monotonically increasing). Their raw values always go up, so OLS on the raw counter would always predict breaching any capacity — meaningless. Using rate() converts them to per-second rates (e.g., bytes/s), which have real capacity ceilings (like 10 GB/s link bandwidth). The forecaster uses the PromQL string from rules.yml directly, which already includes rate().

8 Tier 2 ML — MOMENT Anomaly Sidecar

Located in tools/infer/moment_server.py. Runs as a FastAPI service on port 8083.

What is MOMENT-1-large?

MOMENT is a time-series foundation model developed by AutonLab (Carnegie Mellon). It was pre-trained on a massive corpus of time series data (MOIRAI-style). We use it in reconstruction mode: given a 512-step window of multivariate UPF data, MOMENT encodes it to an embedding, then a reconstruction head decodes it back. High reconstruction error → anomaly.

Architecture: Encoder + Head

Input: (n_channels × 512 steps) of UPF metrics
       [pfcp_sessions, N3_rx_bytes, N3_tx_bytes, N6_rx_bytes, N6_tx_bytes,
        N3_rx_pkts, N3_tx_pkts, port_dropped_N3, port_dropped_N6,
        DL_efficiency, go_goroutines, go_heap_alloc, ...]

        │  z-score normalize each channel independently
        ▼
   MOMENT-1-large Encoder (frozen — never fine-tuned)
        │  Transformer backbone, ~4 GB RAM
        │  Produces dense embedding of the window
        ▼
   ReconstructionAnomalyHead (trained on UPF data)
        │  Encoder: Linear(emb_dim→256) → GELU → Linear(256→128)
        │  Decoder: Linear(128→256) → GELU → Linear(256→emb_dim)
        │  Loss: MSE reconstruction error
        ▼
   anomaly_score = MSE(embedding, reconstructed_embedding)

   anomaly = score >= threshold (calibrated at training time to 0.167)

Graceful Degradation

The sidecar has three operating levels:

LevelConditionBehavior

Statistical Features Fallback

def _statistical_features_np(window):  # window: (n_channels, seq_len)
    # Per channel: [mean, std, max, min, (last-first), autocorr]
    # Total output: n_channels × 6 dimensional vector
    feats = [window.mean(-1), window.std(-1), window.max(-1),
             window.min(-1), window[:,-1]-window[:,0],
             (window[:,1:]*window[:,:-1]).mean(-1)]
    return np.concatenate(feats, axis=0)

Per-Channel Anomaly Attribution

# Approximate which channels are most anomalous:
ch_var   = window.var(axis=-1)          # variance per channel
total_var = ch_var.sum()
ch_scores = { name: (ch_var[i] / total_var) * total_score
              for i, name in enumerate(channel_names) }
# Top anomalous channels: those where ch_score >= threshold * 2.0
top_channels = sorted by ch_score, descending

Confidence Calculation

confidence = clamp(1.0 - exp(-(score - threshold) / normal_std), 0.0, 1.0)
# Interpretation:
# score barely above threshold → confidence near 0 (uncertain)
# score >> threshold           → confidence near 1.0 (certain anomaly)

Training Pipeline

Run: cd tools && python train/prepare_dataset.py && python train/train_moment.py

  1. prepare_dataset.py: Reads prometheus_full_export_20260622_115327.csv (~13 days of UPF data). Slices into 512-step overlapping windows. Saves to moment_windows.npz.
  2. train_moment.py: Loads windows, runs MOMENT encoder (frozen), trains only the ReconstructionAnomalyHead (linear probing). 50 epochs. Calibrates threshold at 95th percentile of training scores. Saves moment_head.pt, moment_threshold.json.

9 Tier 2 ML — Chronos-2 Forecasting Sidecar

Located in tools/infer/chronos_server.py. Runs on port 8084. Uses Amazon's Chronos-T5-Small probabilistic forecasting model.

What Chronos Does

Given the last 512 steps (128 minutes at 15s cadence) of a uoi_value (utilization-of-interest), Chronos samples 20 Monte Carlo paths of the future and returns percentile forecasts (p10/p50/p90). It's zero-shot — trained on a large corpus of diverse time series, no fine-tuning required for our UPF data.

Three Forecast Horizons

HorizonStepsDurationMethod
short205 minutesDirect Chronos-2 output (most accurate)
medium2401 hourDirect for first 64 steps, then linear extrapolation with widening uncertainty bands (sqrt(step) spread)
long14406 hoursSTL hybrid: Chronos direct for first 20 steps, STL seasonal profile + Chronos slope for remaining 1420 steps

Chronos-T5-Small practical limit

The model has a practical prediction limit of ~64 steps. Beyond that, quality degrades. That's why medium/long horizons use extrapolation rather than running the model for 240/1440 steps directly. The 5-minute direct window is the most trustworthy.

Breach Probability Calculation

thr = uoi_threshold  # calibrated from training data
# 20 sample paths from Chronos:
breach_prob = mean( (samples > thr).any(axis=-1) )
# = fraction of the 20 paths where value breaches threshold at any point

# Thresholds:
# < 0.4 → low confidence   → ETA not shown
# 0.4–0.7 → medium         → ETA shown with caveat
# > 0.7 → high             → event promoted to critical

STL Hybrid Long-Horizon Forecast

# For 6-hour forecast:
# 1. Run Chronos for first 20 steps (5 min) — direct
# 2. For remaining 1420 steps:
#    a. Load STL hourly profile for uoi_session_component (from stl-sidecar)
#    b. For each future timestamp, look up hourly_mean[hour] from STL profile
#    c. Add Chronos-derived slope correction
#    d. Uncertainty band grows proportionally with step index

pred_val = seasonal_mean + slope_per_step * (short_steps + i)
spread   = seasonal_std_at_that_hour

Naive Baseline Fallback

When Chronos isn't installed or fails:

# Simple linear extrapolation from last 10 context values:
slope = polyfit(arange(10), context[-10:], 1)[0]
median_fc = last_val + slope * steps
std_est = std(context[-20:])
# Returns p10 = median - 1.28*std, p90 = median + 1.28*std

// Calls: GET http://victoriametrics:8428/api/v1/label/__name__/values

Why a dynamic allowlist instead of a static one?

When new UPF nodes or scrape targets are added, new metrics appear in VM automatically. A static allowlist would require code changes. The dynamic approach also means the LLM can never query metrics that don't exist in the target environment — it's environment-specific security.

19 Cross-Questioning Q&A Prep

Q: What does a UPF do and why does it need monitoring?
A UPF (User Plane Function) in 5G is the data forwarding element — all subscriber internet traffic flows through it. Monitoring matters because capacity failures affect millions of users simultaneously. The key metrics are session count (how many users connected), throughput (N3/N6 bytes/s), and packet drops (quality indicator). Our stack detects anomalies in real-time and predicts capacity breaches hours before they happen.
Q: How does the z-score rule avoid missing a spike that's in the rolling window?
The baseline is computed from all values except the last one (values[:len-1]). The spike value is only the observed data point (values[len-1]). This means the spike can't inflate its own baseline distribution and self-suppress the alert. If the spike were included in the mean/std calculation, it would move both closer to the spike value, reducing the z-score.
Q: Why are port_bytes_count and port_dropped_count counters, not gauges?
They are Prometheus Counters (monotonically increasing) because they measure cumulative bytes/packets transferred since process start. To get a rate (bytes/second), you use rate(port_bytes_count[5m]) in PromQL. The simulator models per-second rates and calls counter.Add(rate × dt) each tick. In flatline mode, rate → 0 so the counter stops incrementing but never resets — you detect the flatline by observing rate() → 0.
Q: What is the difference between reactive and predictive anomaly events?
Reactive (event_type="reactive"): something anomalous is happening RIGHT NOW. Detected by z-score, trend, or threshold rules that fire when the current observed value is statistically extreme. Predictive (event_type="predictive"): a linear regression (OLS) over the recent window is extrapolated forward by 1 hour, and if the trend line hits a capacity ceiling before then, a predictive event fires. These give operators advance warning. The LLM system prompt explicitly instructs the model to use different language for each type ("is spiking" vs "is projected to breach").
Q: How does the dual-ingest (Prometheus + federation fallback) work?
VictoriaMetrics receives data via two simultaneous paths: (1) Primary: Prometheus pushes to http://victoriametrics:8428/api/v1/write immediately after each 15-second scrape. (2) Fallback: VictoriaMetrics promscrape polls the Prometheus /federate endpoint every 15 seconds. Both paths write to the same TSDB. If remote_write lags (network hiccup, VM temporarily overwhelmed), the federation scrape fills the gap. VM deduplicates by timestamp so no data is double-counted.
Q: Why does MOMENT need 512 input steps? What is that time-wise?
512 steps × 15 seconds per step = 7,680 seconds = 128 minutes of UPF history. MOMENT-1-large was pre-trained on this fixed context window. Our training uses sliding windows of 512 steps over the 76k-row dataset. The encoder generates an embedding from the full 128-minute multivariate pattern, which the head then scores for anomaly. The window must be exactly 512 steps because MOMENT's positional encoding is fixed.
Q: Why is the MOMENT sidecar never exposed through Caddy?
Security policy. MOMENT runs on the metrics-backend internal network only. The detection and analysis services call it by internal Docker DNS (http://moment-sidecar:8083). There's no public API for ML inference — only the analysis service's /api/* endpoints are public-facing. This also prevents abuse of the inference endpoint (it's compute-intensive and has no rate limiting).
Q: What happens when the LLM produces malformed PromQL?
The validator catches it at the syntax layer (parser.ParseExpr()) and returns a JSON error: {"error":"PromQL validation failed: syntax error at ..."}. This error is appended as a tool result to the conversation — it is NOT fatal. The LLM reads the error message and reformulates the query. This is the standard OpenAI-compatible tool-calling pattern: tool results (including errors) are fed back to the model for correction. Up to 4 iterations are allowed before giving up.
Q: What is the N3 vs N6 interface distinction?
N3 is the interface between the UPF and the Radio Access Network (phone towers). N6 is the interface between the UPF and the internet (PDN — Packet Data Network). In normal download traffic: user's phone → tower → N3 rx (UPF inbound from RAN) → UPF routes packet → N6 tx (UPF outbound to internet). The simulator models N3 at 120% of base traffic and N6 at 120% on the other direction (downloads dominate, so N3 rx and N6 tx carry more).
Q: How does the Chronos breach probability work?
Chronos-T5-Small samples 20 Monte Carlo forecast paths of uoi_value over the next 5 minutes. breach_probability is the fraction of those 20 paths where the value exceeds the UOI threshold at any point. Example: if 14 of 20 paths breach the threshold, breach_probability = 0.70. Thresholds: < 0.4 = low (ETA not shown), 0.4–0.7 = medium (ETA shown), > 0.7 = high (critical alert).
Q: Why use OLS (Ordinary Least Squares) for forecasting instead of a neural model?
OLS runs synchronously in the 60-second detection poll and must complete in milliseconds. Neural models (Chronos, MOMENT) are too slow for synchronous use. OLS also produces an interpretable R² goodness-of-fit score that's stored in the event's confidence field. The design deliberately uses a statistical method for the reactive/fast path (Tier 1 + 3) and neural models for the analytical/slow path (Tier 2, called during RCA generation).
Q: Where are secrets stored and how are they passed to services?
Secrets are stored in .env (gitignored) and injected as environment variables via Docker Compose's environment: blocks. The secrets/ directory exists but is gitignored and holds nothing committed. The README notes that VictoriaMetrics credentials appear in process args (visible via docker inspect) and recommends using Kubernetes Secrets with env refs for production. For the Caddy admin password, only the bcrypt hash (not plaintext) is stored in the Caddyfile.
Q: What does "degraded mode" mean for the ML sidecars?
Each Python sidecar (ml-infer, moment-sidecar, chronos-sidecar, stl-sidecar) catches all exceptions at startup and sets available: False in its state rather than crashing. The /health endpoint returns {"available": false, "error": "threshold file not found"}. When called by the detection or analysis service, the sidecar returns {"available": false, "anomaly": false} and the caller continues without ML enrichment. This means the stack runs and does Tier 1 detection even before models are trained.
Q: What happens at 02:00 UTC every night?
The export-job service's supercronic daemon fires the export binary. For each metric in EXPORT_METRICS: (1) checks MinIO for a .done sentinel file — if present, skips (idempotent). (2) Queries VictoriaMetrics for the past 24h at 15s resolution. (3) Encodes the timeseries as Apache Parquet with schema {timestamp_unix_ms, value, labels}. (4) Uploads to MinIO at {metric}/date={YYYY-MM-DD}/. (5) Writes the .done sentinel. These Parquet files are the training dataset for MOMENT and Chronos retraining.
Q: Why does the Forecast page always show all 4 metrics, even when no anomaly is firing?
Design decision to avoid a confusing empty state. The Forecast page uses a static FORECAST_METRICS constant and queries VictoriaMetrics instant API (/api/v1/query) directly — not the anomaly SQLite. Cards show current utilization % and raw value at all times. When the OLS forecaster is silent (normal conditions, no capacity breach projected), cards show something like "sessions: 1,200,000 / 2,000,000 capacity = 60%". Only when a predictive event exists does an ETA badge appear. This is documented in both the README and the component code.
Q: What is the STL period=96 and why does it matter?
STL (Seasonal-Trend decomposition using LOESS) requires you to specify the seasonal period. Period=96 means 96 time steps × 15 seconds = 1440 seconds = 24 hours. This captures the diurnal (daily) cycle — traffic peaks at 14:00 and troughs at 02:00. A period of 96×7=672 would capture weekly patterns, but our dataset is only 1.71 days so there's insufficient data for weekly decomposition. The STL sidecar warns about this limitation via data_coverage_days in every response.
Q: How is the analysis service's Basic Auth different from Caddy's Basic Auth?
There are TWO layers of authentication: (1) Caddy Basic Auth protects the raw infrastructure UIs at /vm/* and /minio/*. Credentials: CADDY_ADMIN_USER / CADDY_ADMIN_PASS_HASH (bcrypt). (2) Analysis Service Basic Auth protects all /api/* endpoints (chat, anomalies, PromQL). Credentials: ANALYSIS_AUTH_USER / ANALYSIS_AUTH_PASSWORD (plaintext in env, checked in Go middleware). The React frontend, Grafana, and direct VM access all use their own separate credential systems.
Q: What is the `hf-cache` volume shared between MOMENT and Chronos sidecars?
Both moment-sidecar and chronos-sidecar download their model weights from HuggingFace on first start. The hf-cache named Docker volume is mounted at /hf-cache in both containers (HF_HOME=/hf-cache). HuggingFace's library stores downloaded weights in HF_HOME. By sharing the volume: (1) models only download once, (2) container restarts don't re-download, (3) both sidecars benefit from the same cache. Chronos sidecar also runs with TRANSFORMERS_OFFLINE=1 after first download to prevent internet access on metrics-backend.
Q: How would you add a new UPF metric to monitor?
Four places to update: (1) config/detection/rules.yml: add a new metric entry with zscore/threshold/trend rules. (2) config/prometheus/prometheus.yml: ensure the new metric isn't PII-stripped (check write_relabel_configs). (3) .env: add the metric name to EXPORT_METRICS for nightly Parquet export. (4) frontend/src/lib/metrics.ts: add display name and formatting. Then: docker compose restart detection (no VM restart needed; allowlist auto-refreshes in 5 minutes).
